# 审计检查清单

对应 SKILL.md 第二阶段的逐项扫描。每项都是可执行的检查动作，命中即记录 `文件:方法:代码路径` 与证据。
**没有证据的条目不得写进报告。**

---

## 0. 跨类别通用：边界条件

任何扫描类别遇到以下输入都要检查：

- 空集合 / 空字符串 / 单元素 / 超大批量
- `0`、负数、越界计数（如 `completed > total`）
- 缺失字段、`null`、类型不符、未知枚举值
- 字符串按字符截断破坏 unicode / emoji / 代理对
- 时区、时间戳精度、时钟回拨
- 网络：超时、断网、非 2xx、限流、无效 JSON、流中断、用户取消、无限重试
- UI：`320px` 逻辑宽度、动态长文本、字体放大、`SafeArea`、`viewInsets.bottom`

---

## 1. 数据一致性

- [ ] 实体写入后是否遗漏 `version` 更新（导致乐观锁失效 / 陈旧写入成功）？
- [ ] 是否遗漏 `timestamp` / `updated_at` 更新（导致排序、同步、缓存判断错误）？
- [ ] 是否遗漏 **cache invalidation**（读到的旧缓存覆盖新值）？
- [ ] 是否遗漏 **validation invalidation**（校验结果缓存未随数据变化失效）？
- [ ] 是否遗漏 **related entity update**（A 变了但 B 未同步）？
- [ ] 一对多 / 级联关系：删除或更新父实体后，子实体是否一致？
- [ ] 去规范化字段（冗余计数、汇总、状态镜像）是否与源数据同步？
- [ ] schema 版本号是否唯一、准确描述实际 schema？新增表/列/索引是否伴随**版本递增**与迁移？
- [ ] 迁移是否**幂等**、覆盖**已安装旧版本**，而不只是 fresh install？
- [ ] 是否存在"仓库内 lazy `ensureSchema` 补建表"等**重复 schema 所有权**，绕过版本机制？
- [ ] `ConflictAlgorithm.replace` / upsert 是否会**删除并重插**，抹掉历史或触发级联删除？
- [ ] 重复 create / 重试调用是否幂等？
- [ ] 外键 / 应用层校验是否保证关联实体合法性（如子记录指向的父记录必须存在且属主正确）？
- [ ] 序列化格式（JSON key、枚举序号、默认值）变化是否与**已持久化数据**兼容？
- [ ] 软删除 / 回收站 / 版本记录是否保持可恢复且不与主记录不一致？

## 2. 调用链完整性

对每个核心功能绘制：

```text
入口
 ↓
service
 ↓
repository
 ↓
database
```

- [ ] 是否存在**绕过 service 直接访问数据库**的路径？
- [ ] 是否存在**隐藏写入口**（未被调用链覆盖的写路径、批处理、迁移脚本、后台任务）？
- [ ] 修改某实体时，是否穷举了它的**所有写入口 / 读取入口 / 状态变化入口**？遗漏的入口是否会产生不一致？
- [ ] 是否存在 **unawaited** 异步调用（fire-and-forget 的 DB 写、回调、通知）导致顺序不定？
- [ ] 错误是否被吞掉（空 catch、只 log、返回无意义 null fallback、`dynamic` 掩盖）？
- [ ] 取消 / 超时是否从 UI 一路传播到网络与数据库层？
- [ ] 是否存在**只在测试中构造**的服务（未被生产 composition root 接入）却按"已交付"汇报？
- [ ] 状态变更、持久化、UI 通知三者的先后顺序是否明确且被保证？
- [ ] 回调是否跨层（DB 回调里做业务/UI 判断），绕过既定契约？
- [ ] 是否有"写了没人用"或"用了不存在的"分支？

---

## 3. 状态机审计

- [ ] 是否列出**所有 enum / state** 及合法转换？
- [ ] 非法转换是被**阻止**，还是只是"当前没有触发"？
- [ ] 是否存在非法后向转换（如 `completed → generating`、`validating → receiving`）？
- [ ] 是否存在**无法恢复状态**（卡住且无出口）？
- [ ] 是否存在**永久失败状态**（失败后无重试/回滚路径）？
- [ ] 终态是否明确？终态后是否仍可能被迟到事件改写？
- [ ] 状态的真实 **Single Source of Truth** 是哪个（Widget / Provider / Service / DB）？是否有多处同时被当作真相？
- [ ] 状态**显示**是否与持久化状态一致？乐观 UI 与持久化分叉时以谁为准？
- [ ] pause / cancel / recover / retry 的转移是否完备且有序？
- [ ] 是否有 lease / version / compare-and-set 防止**过期写入**覆盖新状态？
- [ ] 状态回调是否被 `await`？未 await 的多个回调是否乱序写库？

---

## 4. 并发与事务

- [ ] 穷举所有 `read → modify → write` 流程。
- [ ] 是否存在 **race condition**（共享可变字段被并发覆盖）？
- [ ] 是否存在 **lost update**（两个写者相互覆盖）？
- [ ] 是否存在 **stale data**（读到旧值后基于旧值决策）？
- [ ] 是否缺失 **optimistic lock**（version / revision / CAS）？
- [ ] 并发上限 > 1 的路径是否被真实覆盖（而非只测串行路径）？
- [ ] 重试 / 重复点击 / 双次提交是否产生重复记录或双重副作用？
- [ ] 旧请求的迟到响应是否会覆盖新请求结果？（需 generation/task handle 丢弃）
- [ ] Widget `dispose` 后是否仍更新 `ValueNotifier` / `setState` / 订阅？
- [ ] Timer / StreamSubscription 是否在终态、取消、异常时被取消？
- [ ] 事务边界：需要原子性的多步写入是否包在 transaction 中？
- [ ] 失败是否**完整 rollback**？会不会留下半完成状态（如永久 `generating`）？
- [ ] 持久化与"事件发布/UI 通知"的顺序是否会暴露不一致中间态？
- [ ] 防抖/合并写入在**取消/异常/退出**时是否丢失未确认数据？
- [ ] 迁移过程中失败是否让数据库处于不可用状态？
- [ ] 是否用 `Future.delayed` 掩盖竞态，而非真正解决？

---

## 5. API / 协议兼容性

- [ ] **schema** 变更是否破坏已存数据或旧客户端？
- [ ] **parser** 是否能容忍新增/缺失字段、未知枚举、类型宽松变化？
- [ ] **serialization** 格式（key、顺序、精度、默认值）变化是否破坏兼容？
- [ ] **version** 是否递增并对外可协商？
- [ ] 是否存在 **breaking change**（删除字段、改语义、收紧校验拒绝合法旧数据）？
- [ ] 输入输出契约是否有明确边界与错误映射（非 2xx、无效 JSON、流中断）？
- [ ] 是否复用统一模型/Client，还是各调用点各自实现协议导致漂移？

---

## 6. 测试真实性

核心问题：**"如果真实代码坏掉，这个测试会失败吗？"**

- [ ] 是否只断言了 mock / fake / stub 的行为，没走真实逻辑？
- [ ] **测试路径是否等于生产路径**？（重点：fake 通过、production 失败）
- [ ] 是否存在 `测试 A == A` 而 `生产 A != B` 的错位（fixture 与生产接线不同）？
- [ ] test helper 是否悄悄替换了被测对象（注入 fake 而非真实实现）？
- [ ] 高风险分支是否有 fixture：并发上限 > 1、**运行中**取消/暂停（非预取消）、多会话竞争、中断恢复
- [ ] 迁移测试是否断言**语义**（新版本号、新表、新索引、旧数据保留），而非仅"未抛异常"？
- [ ] 并发测试是否用 barrier / latch 真正交错，而非顺序执行后声称覆盖竞态？
- [ ] 真出现的 bug 是否补了回归测试？
- [ ] 是否存在被 skip / `expect(..., anything)` / 宽松匹配掩盖的测试？
- [ ] 报告中的测试数量、命令、结果是否与**实际执行输出**一致？
- [ ] 是否存在为了通过而修改预期值、删除或弱化测试？

---

## 7. 性能风险

- [ ] 是否存在 **O(n²)** 或更差（嵌套遍历、重复全量扫描）？
- [ ] 是否存在**大量内存复制**（每帧/每 chunk 复制大集合、字符串反复拼接）？
- [ ] 是否存在**全量加载**（一次性载入全部消息/资源/记录，无分页）？
- [ ] 是否存在 **UI 阻塞**（同步重活在主 isolate、每 token 重建整页）？
- [ ] 是否存在**大事务**（长事务锁库、事务内做网络/IO）？
- [ ] **规模扩大后的行为**：消息数 ×10、资源数 ×10、并发 ×n 时是否退化？
- [ ] 是否有重复查询 / N+1 访问（循环内查库）？
- [ ] 索引是否覆盖高频查询条件？

---

## 8. 文档一致性

比较：**文档声明 VS 代码事实**

- [ ] 实现报告 / 验收文档的每条 claim 是否都能在代码中找到对应实现？
- [ ] 是否存在**夸大声明**（"已完全解决""无风险"但代码不支持）？
- [ ] 是否存在**缺失限制**（未声明的前提、兼容范围、已知缺口）？
- [ ] 是否存在**错误状态**（如 `STATUS.md` 解锁了实际未完成的阶段）？
- [ ] 报告中的命令与计数是否可复现、数字是否与实际一致？
- [ ] 架构文档与当前实现（层、契约、数据模型）是否仍然一致？
- [ ] 注释 / 文档字符串是否描述了已改变的行为？
- [ ] 版本号、schema 号、API 路径在文档与代码间是否一致？

## 补充 A. 安全与数据边界

- [ ] 是否提交/打印 API Key、Token、Password、Cookie、OAuth 凭证、私有证书？
- [ ] 日志是否输出密钥、Authorization Header、完整 Token、用户敏感数据？
- [ ] SQL 是否使用参数绑定？（禁止字符串拼接）
- [ ] 是否存在越权访问（跨用户/跨会话读写他人数据）？
- [ ] 删除操作是否保护用户数据，是否可能误删（覆盖导入、清库）？
- [ ] 外部输入（LLM 返回、导入文件、剪贴板）是否被当作可信数据使用？

---

## 补充 B. 隐藏回归与爆炸半径

- [ ] 删除/重命名符号前是否 `rg` 检查动态引用（route、provider、测试、migration、平台代码）？
- [ ] 公共签名变更是否更新了**所有**调用方？
- [ ] 枚举顺序 / index / 序列化 key 变化是否破坏已存 SQLite / SharedPreferences / 文件数据？
- [ ] 默认值变更是否改变既有行为？
- [ ] schema 变更是否遗漏版本递增（最隐蔽的一类回归）？
- [ ] 一处修复是否被另一处重复实现反向抵消？
- [ ] 跨平台（Linux/Windows/Android/macOS/iOS）是否有一处改动破坏另一平台？

## 附：LT 流式输出专项（对应 AGENTS.md Token 规范）

- [ ] 网络层是否**立即**消费 chunk，不因 UI 节流阻塞读取？
- [ ] 是否使用单一累积缓冲区 + 单调 cursor（不重复拼接已展示前缀）？
- [ ] UI 刷新是否有节流下限（默认 30ms；预览型 180ms），而非每 chunk 整页 rebuild？
- [ ] 流结束/取消/异常/失效时是否执行**最终 flush 或明确清空**并取消 Timer/订阅？
- [ ] 是否通过 generation/task handle 丢弃过期响应（旧请求不覆盖新请求）？
- [ ] token 统计是否以服务端 usage 为准，缺失时才用统一估算器估算一次？
- [ ] 持久化 token 总量是否合并写入并防抖，且取消/异常不丢已确认 usage？
- [ ] reasoning / 正文 / 进度 / 滚动是否使用最小粒度 notifier，避免整树重建？
- [ ] 是否覆盖：高频小 chunk、单个大 chunk、空 chunk、结束时仍有缓冲、取消后迟到 chunk、请求切换、usage 缺失？
